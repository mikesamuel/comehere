Rebooting printf debugging
Towards scanf debugging

Printf debugging is no substitute for robust, automated test suites, but it is a critical practice in exploring, understanding, and debugging code. JavaScript introduced the debugger keyword almost thirty years ago to aid in debugging. But the language has only added one feature since then to explicitly aid debugging: console.

This showcases a syntactic feature that simplifies both live programming and a robust investigate → fix → guard (against regressions) developer flow by allowing mixing non-production live/test code into production contexts where it can refer to encapsulated implementation details by name, without affecting the semantics of code in production.

Below, you can see the proposal in action! Imagine you're debugging a piece of code. You suspect that some inputs to a deeply nested helper function will help you understand what's going on. But getting the right inputs to that function requires reverse engineering a program input that would cause the desired function call. That's now unnecessary. Simply tell the program to COMEHERE with the inputs you want, and it will.

⬑ That play button runs the code. The selector lets you pick which COMEHERE block to run.

On the left you can see a sample program that uses COMEHERE:with to cause a function to be called with certain inputs. And then it logs those outputs. It's printf debugging on steroids!

Hit the play button below the editor to see the console output from the COMEHERE block body. Below are the parts of a COMEHERE block:

  • There's a syntactic marker. This is placeholder syntax that lets us integrate the proposal into existing toolchains.
  • If there's a quoted string right after the open parenthesis, it's a description. It's optional but providing it helps tools like the developer console make it easy to pick the right block when interactively debugging a module.
  • Then there are zero or more assignments. This lets the developer control the values of inputs to functions and class instances that contain the target COMEHERE block.
  • The calling framework may provide goodies, extra visualization, testing, or live programming affordances that should not be available to production code. They get bound to this name if provided.
  • Finally, there's a body, statements to run that help the developer understand their code.

COMEHERE is inspired by the Come From esoteric language which jokingly advanced the idea that transfers of control could be specified, not in the context from which control transfers like a regular instruction, but in the context to which control transfers.

COMEHERE works by “driving control” to the block. Look at the top line of the translation on the right above; when seeking_0 is 1, it'll call the containing function, and within it, will log some information about intermediate values.

With COMEHERE, loading the module has the side-effect of letting the user (via debugHooks) choose what to debug and logging valuable information. No need to reverse engineer program state to explore what's going wrong. But when seeking_0 is 0, it has no semantic effect on the code.

Aspect-Oriented Programming (AOP) also allows for balancing separate concerns by transforming code at strategic locations, and has been jokingly described as a formalization of Come From. AOP focuses on assembling production code from multiple separately specified and maintained aspects. This work differs in that it focuses on preserving the semantics of production code, and allowing separate runs of the same program to work towards different non-production goals.

Postconditions

Another thing to note is that, when one or more COMEHERE blocks occur right after a return statement, they can run and the special expression Function.return refers to the returned value. (That syntax only works inside those blocks)

Asynchronous await calls pause execution, and can be a source of re-entrancy. Below is an example of an async function that reenters itself while paused (modulo setTimeout nondeterminism). 

    async function f(desc, promise, recursed = false) {
      if (!recursed) {
        setTimeout(
          () => { f("reentrant", Promise.resolve(234), true) },
          0
        );
      }

      let r = await promise;
      COMEHERE:with(
        desc = "synthesized",
        promise = new Promise(
          (resolve) => { setTimeout(() => resolve(123), 100); }
        )
      ) {
        // should log "synthesized result is 123", not "reentrant result is 234"
        console.log(desc, "result is", r);
      }
    }

TODO: our isActiveCall guards prevent observing the wrong result due to reentrancy, but the try/finally around the synthesized call probably needs to await in the try when the callee is async or else the finally will trigger before the COMEHERE is reached. In the case where the callee is an iterator, we might want to close it. Maybe a try body helper could switch on the function species at runtime, instead of trying to generate statements differently for each species.

JavaScript's proposed function decorators might require some special handling. Decorators, unlike function proxies, intercept simple calls by name. A decorator that wraps a function in a way that recurses with different arguments before invoking with the arguments would observe activeFns in an unintentional state. Depending on how decorators end up being incorporated in the language, supporting them might involve desugaring function hoisting and decorator application.

Modulus/remainder subtleties are a source of confusion, but the x >= 0 check means that neither % operand should ever be negative. Still, that COMEHERE block can cause a call to that helper with an input that should never reach it.

This example introduces a testing affordance, discussed later in more detail. The idea is that the lines in the string like $ isOdd(0) are executed in the context of the nested helper function, so that code is testing it with inputs that would not reach it in normal production use.

Changes to branch conditions

In some programming languages, the semantics of branch condition expressions affect whether later expressions are allowed via type predicate (e.g. Typed Racket's occurrence typing or TypeScript's narrowing predicates). For example, in TypeScript like if (typeof s === 'string') { f(s); }, the call to f(s) might only be well-typed because the type checker knows that s refers to a string value.

Adding extra conditions under which that condition is true could cause expressions to fail to type check that otherwise would. In a language like TypeScript, where types are erased and do not affect the semantics of dispatch, and do not need to be sound for memory representation assumptions to hold, one could just lie to the compiler, for example via a higher-order type predicate function that takes a type guard application and extra conditions and uses as false to logically union them but in a way that pretends to preserve the lower-order guard's postconditions. Type checking and narrowing is important, but like encapsulation, relaxing it to allow program exploration and testing is good, and running programs in a separate optimistic and fault-tolerant interpreted runtime is always possible.

Mutable global state

Using mutable global variables to track COMEHERE seeking state works in JavaScript because it is event loop concurrent, but most other languages' runtimes are not. Passing seeking state via extra function arguments would strongly anchor seeking state to a particular stack frame, and ease adapting this scheme to languages that have reentrancy due to threading, but that causes its own problems: notably JavaScript allows calls with more arguments than the callee expects, and runtime introspection can expose information about adapted function signatures. If the seeking information captured which thread was seeking, or was thread-local, and thread-locals were robust agains optimizations like coroutine work stealing, then that would address this problem.

Visualizing Intermediates

We asked more than two veteran printf-debuggers, “if you could make one change to printf to make it even more obviously the best way to debug programs, what would it be?” Unanimously, they wanted to print a value alongside the code that produced it.

Any variable that starts with two dollar-signs ($$0, $$foo, etc.), and which is not defined in the containing module is treated specially:

  • We create a definition in the deepest function or module body that contains all references to that variable.
  • When the variable is assigned, we store information about the code that derived the new value.
  • When the variable is used in a spread (...$$0), the code precedes the value.

That enables wrapping a complex intermediate expression in ($$0 = complexIntermediate()) followed by console.log(...$$0).

This $$ feature nice for reducing the friction when visualizing program state, but it comes with risks. Entangling the semantics of string-producing expressions with lexical details of code risks making life harder for IDE plugin developers who aim to provide semantics-preserving refactoring options. This kind of feature has proven valuable in other contexts:

  • Eric Smith extended Python3's f"…" string syntax to directly include code in the string produced.
  • Lerner's Projection Boxes use identifiers that appear in code in table headers but do not directly affect string values in the program.
  • The power-assert JavaScript library contextualizes failing predicates in test code but does not typically affect string values that are used outside reporting tests that fail regardless.
  • Rust's dbg! macro shows the expression and result, but only in strings sent to stderr.

For a higher degree of interactivity we can run a REPL (Read-Eval-Print-Loop), in the context of hidden implementation details that might need debugging. This code includes a helper and local state encapsulated inside a function which a typical programmer playground can't access. 

function* fibonaccis(a = 0, b = 1) {
  let [x, y] = [a, b];
  function update() {
    [x, y] = [y, x + y];
  }

  COMEHERE:with("fib-REPL", a = 0n, b = 1n) {
    // Run a REPL in the context of the helper
    // function update() and hidden state x&y.
    let code = 'update(); [x, y]';
    let beforePrompt = '';
    while (true) {
      code = prompt(`${beforePrompt}$`, code);  // Read
      if (!code) { break };
      let result = eval(code);   // Eval
      console.log('->', result); // Print
      beforePrompt = `-> ${result}\n`;
    }                            // Loop
  }

  while (true) {
    update();
    yield x;
  }
}

From debugging to regression testing

Once we've debugged a piece of code, it'd be nice to guard against future breakage, and maybe we've already got a REPL log, a notebook, of what we did when debugging. It'd be super-nice to be able to edit that notebook down to something that can serve as a regression test. Our extra goody-bag input comes in handy here. Production code shouldn't depend on test harness code (Node Security Roadmap by M.Samuel et al.), but a test harness that iterates over, and runs each COMEHERE block and collects test results can inject test affordances.

That way of specifying a test is inspired by the E programming (Mark Miller et al, "E: Open source distributed capabilities," 2001) and its documentation and testing toolchain, especially updoc. While the authors learned from updoc, Python now supports this via the doctest module, though not for encapsulated functions.

Wrapping up

In summary, COMEHERE provides a way to break encapsulation where you need it: in non-production contexts when live programming or closed-box testing. This contributes an AST transform for JavaScript that demonstrates how to drive control to where encapsulated implementation details can be referred to by name. This is an enabling feature; it eases printf-style debugging, live programming practices like bolting a user-interface on plain old code for testing and visualization, running a hand-crafted REPL in a nested context, and allowing printf-debugging without having to orchestrate outer loops to get control to the code under investigation. As such, it might serve as a useful building block for more syntactically-sugary debugging and testing features.
